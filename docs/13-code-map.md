# Code map

> **Last updated:** 2026-10-27

Every file in the project and what it does. Written for somebody who has just
cloned the repository and wants to know where anything lives before changing
it.

The tables are generated by `php artisan atlas:code-map`, and a test fails if
they are out of date: run it after adding, removing or renaming a file, or
changing the first line of a class docblock. Every description is that first
line, so an entry cannot disagree with the file it describes. The prose
between the tables is hand-written and the command never touches it.

**Read [09-how-the-system-works.md](09-how-the-system-works.md) first** if you
want the story of what the system does. This page is the index, not the
narrative.

---

## How a request travels

Nothing here is clever, and that is deliberate. Seven people over eight weeks
need an architecture each of them can explain under questioning.

```
Browser
  |     Blade, Tailwind, Alpine for interaction, Chart.js for graphs
routes/
  |     grouped by role prefix
app/Http/Middleware/
  |     auth, then role. Nothing reaches a controller unverified
app/Http/Requests/
  |     is the request well formed?
app/Policies/
  |     may this person do this to this record?
app/Http/Controllers/
  |     validate, hand decisions to a service, return a view
app/Services/
  |     the business rules live here
app/Models/
  |     Eloquent. Relationships, enum casts, scopes
PostgreSQL
```

Three separate questions get three separate files. Moving a ticket asks
whether the request is well formed (`TransitionTicketRequest`), whether this
person may do it (`TicketPolicy`), and whether the move is legal at all
(`TicketService`). Collapse any two and "an engineer closed a ticket assigned
to somebody else" becomes possible.

Scheduled commands enter at the service layer and skip the top three. A
command and a browser request run the same rules. `atlas:prune-telemetry` is
the one exception: it deletes through the models, since nothing else prunes.

| `auth.php` | _no summary in the file_ |
| `console.php` | _no summary in the file_ |
| `web.php` | _no summary in the file_ |
<!-- /code-map -->

`web.php` is grouped by role, so an assistant's URLs sit under
`/assistant`, an engineer's under `/engineer`, and an administrator's under
`/admin`. The grouping is not decoration: the `role` middleware is applied to
the group, so a new screen inherits its protection from where you put it.

One route sits deliberately outside the `auth` group. The calendar feed is
fetched by a phone's calendar app, which cannot sign in, so it authenticates
with a 48 character token in the URL and is rate limited instead.

## app/Http/Middleware/

They answer different questions.

<!-- code-map:app/Http/Middleware/ -->
| File | What it does |
|---|---|
| `EnsureAccountIsActive.php` | Signs out a deactivated account on its next request (FR-106) |
| `EnsurePasswordIsChanged.php` | Stops a user who is still on an administrator-chosen password (Q6) |

`EnsureUserHasRole` is applied per route group: may this role reach this area
at all? `EnsureAccountIsActive` and `EnsurePasswordIsChanged` are appended to
the whole `web` group instead, because a control you have to remember to apply
is one somebody will forget on the next screen they add.

`TelemetrySource` is the only abstraction in the project and it earns its
place. `SimulatedTelemetrySource` invents readings; `SnmpTelemetrySource`

controller or model knows which one answered.

`RiskScoringService` is the module the whole project turns on. It combines
weighted factors, drops any it cannot measure, and rescales the rest so a
missing input never quietly counts as zero.

## app/Providers/

Small, and more of the system passes through it than its size suggests.

<!-- code-map:app/Providers/ -->
| File | What it does |
|---|---|
| `AppServiceProvider.php` | Models whose every write is recorded in audit_logs. Add a model here and |
<!-- /code-map -->

Three things happen here. `AUDITED` lists every model the audit observer
watches, so adding a model to that array is how a table starts being tracked.
The `TelemetrySource` binding reads `atlas.telemetry_driver` and throws on an
unknown value rather than falling back, because a typo silently producing
invented data on a system meant to show real readings is the worst outcome
available. And `toMailUsing()` rewrites the password reset email, which is
where the on screen reset link comes from on a machine with no mail account.

Two configurations run the same suite. `phpunit.xml` uses SQLite in memory
because it is fast and needs nothing installed. `phpunit.pgsql.xml` runs it on
PostgreSQL with TimescaleDB, the database Atlas runs on, in a separate
`atlas_test` database, because each run starts by dropping every table in the
database it uses.

The browser tests in `tests/Browser/` are JavaScript, which the table above
leaves out. Playwright runs them against a Docker stack of their own:
`npm run test:browser`. [07-testing.md](07-testing.md) lists what each covers.

## What is deliberately absent

No repository interfaces. Eloquent is already the data access layer.

No global scope hiding demo rows. A scope that hides data during a
demonstration is worse than the data being visible.

No `mark all OK` button on the checklist. Thirteen questions is thirteen taps,
and a button that answers them all at once makes it possible to submit an
inspection without looking at the machine.

No second database for demo data. One schema, tagged rows.

## Keeping this page honest

Rebuild the tables after adding, renaming or removing a file:

```bash
php artisan atlas:code-map
```

**Give a new class a docblock whose first line says what it does in one
sentence** and it appears here correctly. Nothing is retyped, so an entry
cannot drift from the file it describes.

`atlas:code-map --check` writes nothing and exits 1 when the page is out of
date. `BuildCodeMapTest` runs that check, so adding a file without rebuilding
this page fails the suite rather than quietly leaving the map wrong. That test
matters more than the page does.

Only the tables are managed. Each sits between a pair of markers naming the
directory it lists, like this one for a directory that does not exist:

```
<!-- code-map:app/Example/ -->
<!-- /code-map -->
```

That example names a made-up path deliberately. Writing a real one here would
put a second copy of a live marker in the document, and the command matches
the first it finds.

Edit the prose around them freely. A section named in the command with no
matching marker fails loudly rather than disappearing.
